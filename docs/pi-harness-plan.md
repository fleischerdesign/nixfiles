# Pi Harness

The Pi feature provides a declarative, provider-agnostic coding-agent setup while leaving Pi's
runtime, tool surface, sessions, and extension lifecycle intact. Nix owns configuration; Pi owns
runtime state.

## Current composition

- Pi, provider/model selection, themes, skills, MCP configuration, and credentials are generated by
  the Nix/Home Manager module in `features/dev/pi/`.
- Generic command-line helpers used through Pi's `bash` tool are declared separately through
  `my.features.dev.pi.cliPackages`; the default set is `ripgrep`, `fd`, `jq`, `nil`, `statix`, and `deadnix`.
- Plugin identity, package installation, and generated package paths are derived from the discovered
  plugin modules. The enabled baseline is `context-mode`, `pi-background-tasks`, `pi-goal-x`, `pi-lens`,
  `pi-mcp-adapter`, `pi-subagents`, `pi-web-access`, `rpiv-ask-user-question`, and `rpiv-todo`.
- `pi-goal-x` provides autonomous conversational goal loops (`/goal`, `/goal-direct`), ordered staging
  and migration flows (`/sisyphus`), session-persistent progress checkpoints, and an independent
  completion auditor to prevent premature task completion.
- `pi-lens` provides real-time LSP diagnostics, code-navigation (`symbol_search`, `read_symbol`), and
  linters directly hooked into file modification events, eliminating expensive brute-force token greps.
- `pi-subagents` provides bounded single-agent delegation and isolated multi-agent workflows. Subagents
  run on low-cost models (`deepseek-flash` by default) with strictly bounded turn limits and synthesized
  returns, protecting the parent context window from raw token bloat.
- `rpiv-ask-user-question` provides a structured modal questionnaire when user requirements contain
  actionable ambiguity, preventing costly iterative guesswork.
- `pi-mcp-adapter` exposes configured MCP servers through its proxy configuration. MCP servers are
  declared by the module and are included only when that adapter is enabled.
- The global Pi guidance is `features/dev/pi/AGENTS.md`; repository-specific rules remain in the
  nearest repository `AGENTS.md`.
- Skills are discovered from `features/dev/pi/skills/` and loaded on demand. The current skills are
  `systematic-debugging` and `systematic-refactoring`.
- Sessions, caches, and extension runtime data remain writable under Pi's normal state directories;
  generated settings, models, MCP, authentication, skills, and global guidance remain declarative.

## Operating model

The workflow is intentionally native-first:

1. Read the user request, applicable `AGENTS.md` files, and the relevant code or configuration.
2. Choose a proportionate approach. Use a short plan for substantial or uncertain work; keep small
   obvious edits direct. Use `ask_user_question` when clarification is required.
3. Leverage LSP navigation and diagnostics (`pi-lens`) to locate symbols and verify structural integrity.
4. Implement the smallest coherent change using existing abstractions and contracts.
5. Run checks appropriate to the changed surface, inspect the final diff, and report evidence and
   remaining uncertainty.

Long tasks use Pi's native sessions, branches, compaction, and task mechanisms. A useful handoff
contains the objective and acceptance conditions, user constraints, changed files, completed checks,
open hypotheses or blockers, and the next concrete action. It is updated when the material state
changes; no separate progress-file protocol is required.

## Instruction and skill boundaries

The global file is short and repository-agnostic because it is present in every Pi session. It gives
stable working principles, communication language, proportionate verification, on-demand skills, and
bounded delegation. The repository file supplies `/etc/nixos` commands, topology, invariants, and
deployment rules. Skills contain procedures that are useful only for particular task classes; their
descriptions are precise routing signals and their bodies are loaded only when selected.

The debugging skill uses observation, competing explanations, discriminating experiments, a narrow
fix, and targeted verification. The refactoring skill maps callers and stable behavior, adds
characterization coverage only where useful, and uses expand–contract only when atomic migration is
not possible. Neither skill requires fixed repetition counts, mandatory commits, ceremonial logs, or
full-suite execution for every change.

## Delegation

Delegation is opt-in and capability-based through `pi-subagents`. A subagent is useful for an
independent bounded task using dedicated built-in personas:
- `scout` & `researcher`: Local codebase reconnaissance or external web/doc research.
- `oracle`: Adversarial second opinion on complex plans, risk analysis, and architecture.
- `reviewer`: Focused diff, security, and edge-case review on completed changes.
- `worker`: Self-contained, isolated implementation tasks in decoupled subcomponents.

The parent agent supplies objective, relevant paths, constraints, and a concrete return contract,
then integrates and verifies the result. Subagents return synthesized digests or diff summaries to
prevent context bloat in the parent session. Trivial local searches, tightly coupled single-line edits,
generic "review everything" requests, and uncontrolled recursive fan-out are poor delegation targets.

The feature does not add a second registry, lifecycle framework, permission layer, sandbox, tool
allowlist, mandatory confirmation flow, telemetry service, or paid model-evaluation pipeline.

## Research basis

This design follows Pi's documented context-file, on-demand skill, session, and compaction model and
current long-running-agent research: keep context high-signal, decompose work into tractable slices,
leave structured handoffs, and use separate agents only where independent breadth justifies their
cost. These principles are engineering guidance rather than a claim of benchmark-optimality.
