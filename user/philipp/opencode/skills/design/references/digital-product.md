# Digital Product

## When to load & job

Load this when a decision changes how people encounter the same product across screens, roles, or visits. Decide what persists, who can act on it, and what brings someone back. Use a screen module for the layout of any one stop along the way.

## Inputs

Bring the existing navigation, product vocabulary, roles, object states, and examples of first and repeat use. Take permissions and state transitions from the product and engineering owners. If those aren't settled, draw a proposed model with assumptions marked and leave live actions unwired.

## Decisions & process

Start with the object people return to. If they revisit the same invoice from search, activity, and reminders, give it one stable detail view and carry its name and status across entry points. If people work through a queue, lead with the next action instead; it saves navigation but makes it harder to browse the whole history. Draw both entry points into the same object.

Map who can move that object through its lifecycle. Use the same label when a state means the same thing, but vary the action by role: a submitted invoice can offer “Withdraw” to its author and “Review” to its approver. A shared state model costs coordination across teams; separate screen models make local changes easier but can give people conflicting accounts of the same work.

If someone can get value before setup, onboard them through a first real task and defer preferences. If the task depends on a shared workspace or permissions, explain that dependency up front. For repeat visits, compare resuming unfinished work with a fresh overview: the former saves effort, the latter makes new activity easier to notice.

## Typical mistakes & examples

When the dashboard calls an invoice “Complete” as soon as it's submitted but billing still calls it “Pending,” authors may assume it's paid. Separate submission from payment in the lifecycle, then show both where people make decisions.

## Deliverables & questions for the human

Show the object and state map alongside a linked slice from first task to return visit. Ask which work should be resumable, who owns each transition, and what event warrants bringing someone back.
