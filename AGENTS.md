# Working in this repository

Agent-facing instructions for this NixOS + Home Manager configuration. What the system *is* is in the
[README](README.md) and [`docs/`](docs/README.md); this file only says how to work in it.

## Commands

```bash
nix fmt        # nixfmt over the tree, in place
deadnix --fail # no unused code
statix check   # lint; statix.toml disables repeated_keys, manual_inherit, manual_inherit_from,
               # useless_parens
nix flake check                         # all five hosts evaluate, plus format, statix and deadnix
nix flake check --max-jobs 1            # the same gate, serialised: the answer you can trust under load
nix build .#integrationChecks.x86_64-linux.directory-runtime  # boots Django/Postgres; CI runs it, the loop does not
nix build .#checks.x86_64-linux.<name>  # a single check from checks/, in isolation

nod switch <host>                                                # fleet deploy: build, transfer, activate
nixos-rebuild switch --flake .#<host>                            # one host, locally
nixos-rebuild switch --flake .#<host> --target-host root@<addr>  # one host, remote
```

`nix flake check` is the gate - it is what CI runs and what must pass before a change is done. Read
its whole output, warnings included.

The gate holds the checks that are cheap and deterministic: evaluation, contracts, formatting. The
end-to-end check that boots a Django/Postgres database lives in `integrationChecks`, because it costs
minutes and mirrors the provider's HTTP surface in a stub - a gap there is a fixture gap, not a
defect. CI runs both; the local loop runs the gate.

Every check is deterministic: a real failure reproduces when that one check is
built alone. A failure that does not reproduce is memory pressure, not a defect -
the runtime checks boot a Django/Postgres database and build shells, and this
host has 15 GB. A builder killed by the kernel is reported as a failed check, so
`--max-jobs 1` is the difference between a green gate and a lie. CI already builds
serially for the same reason.

The shell is **fish**, locally and on the hosts: `VAR=value cmd`, `$?`, `${PIPESTATUS[0]}` and
`for … do … done` all fail. Wrap anything non-trivial in `bash -c '…'` or `bash -s` with a heredoc,
and prefer a script file over nested quoting.

## Conventions

- **English** for code, comments, commits and documentation.
- **Conventional Commits**, scoped by area: `fix(home-assistant): …`, `chore(deps): …`.
- **Nix style**: `nixfmt` decides formatting; do not hand-format. A feature is a directory with a
  `nixos.nix` and an `enable` option, loaded on every host and active only where enabled.
- **The inventory decides.** Zones, addresses, names and firewall rules derive from `my.topology`
  and the contract projections; writing one twice means the derivation is missing.
- **Declare, never hand-write.** Caddy vHosts, Authentik blueprints and provider resources
  (databases, users, buckets) are projected from `my.contracts.provides.<name>`.
- **Documents describe the present.** No diaries, no phase plans, no status sections - history
  belongs in commit messages. Where a document and the code disagree, the code is right and the
  document is a bug.

## Do not edit by hand

- `hosts/*/hardware-configuration.nix` - generated by `nixos-generate-config`.
- `secrets/**` - SOPS-encrypted; edit with `sops`, never in plaintext.

## Where the time goes

Measured on `cld-ops-01`, so the recipe below has numbers rather than habit behind it:

| Step | Time | What it means |
|---|---|---|
| `config.networking.hostName` | 1 s | the module system, the contracts and the inventory are not the cost |
| `config.system.build.toplevel.outPath` | 50 s | the derivation graph of one system |
| `nix flake check --no-build` | 70 s | evaluation of every check |
| `nix flake check` | 98 s | the checks themselves add ~28 s |
| `nix flake check --max-jobs 1` | 2-3 min | the same checks, one builder at a time: no false failure under load |

`nix eval` does not use the eval cache; `nix build` does. That is why the daemon
evaluates a host in seconds while a script using `nix eval` pays 50 s every time.

`nix flake check` never instantiates a host toplevel. What costs minutes is a
*build* of the systems, and that happens whenever a shared input changes: `nod`
is one, so a single bump to it invalidates every host closure.

No derivation reads the commit hash. The portal reports the revision its host
*runs*, taken from the reconciler's state at start, so a commit that changes no
evaluated value produces identical closures - and a documentation change does
not roll the fleet.

Path literals need the same care. A literal into the tree (`../../media/x.jpg`)
resolves inside the single `<hash>-source` copy, so its hash covers every file
in the repository: a document would change the store path of a wallpaper. Files
that end up in a derivation are content-addressed with `builtins.path`.

### A change through the gate

1. `nix fmt && deadnix --fail && statix check` - seconds.
2. `nix flake check` - about two minutes warm. It stays the gate; do not replace
   it with `--no-build`, which only proves the checks evaluate. Add `--max-jobs 1`
   while the reconciler is building: parallel builders exhaust memory, and a
   killed builder is indistinguishable from a real failure until you rebuild it.
   A change to the directory or the Authentik provider also builds
   `.#integrationChecks.x86_64-linux.directory-runtime` - that is the check that
   boots the database and drives the shipped binary.
3. Build the host that deploys first, not the fleet:
   `nix build .#nixosConfigurations.<host>.config.system.build.toplevel`.
   The reconciler builds every other host before activating it, and CI proves the
   matrix; building all five locally duplicates both and costs minutes each.
4. One input bump per finished change, not per fixup. A new `nod` revision changes
   the binary's store path, and with it every host closure.

CI builds the host matrix with `max-parallel: 1` on purpose, and should keep it:
matrix jobs run on separate machines with no shared store, each job pushes its
closure to Attic after building, and the next job substitutes what the previous
one produced. Parallel jobs would each build the shared half again.

## Where an assertion belongs

Every statement about this repository has one layer that decides it. Put it there, and only there.

| Layer | Mechanism | What it decides |
|---|---|---|
| Configuration graph | `assertions`, `throw`, option types | a statement about the evaluated configuration |
| Derived artifact | the build itself (schema validation, compilation) | "the artifact is well-formed" |
| Runtime behaviour | `nixosTest` | what a service does when it starts |
| Live fleet | the reconciler's report | the running system matches the declaration |

A `checks` entry is justified for a **fixture**: library code evaluated on synthetic input, where no
other layer can express the statement. Everything else is a statement in the wrong place - it either
duplicates a lower layer or re-states what the generator was told.

### Rules for a new assertion

1. Decide the layer first. If `throw` can decide it, a check is a weaker copy of it.
2. Name the failure it catches in one line, in the file. A check without that line is not merged.
3. It must fail on a plausible change, and no other layer may already catch that failure.
4. A test double models only what the test needs. An unexpected call is recorded, not fatal - the
   provider's own tests own its HTTP surface.
5. A heavy test is selected by risk (changed paths), never run unconditionally.

A check that cannot fail on a plausible change is not a check - it is documentation with a build
job. The named failure is the test of that: if the only sentence it can produce is "the generator
wrote what it was told", the statement belongs in the generator as a `throw`, and the check is
deleted rather than repaired.

So these are never written:

- a check that greps a generated file for a string the generator just wrote into it;
- a check that repeats an assertion another layer already makes;
- a check whose failure message does not name a defect a person could have introduced;
- a test double that must be extended whenever the code under test calls a new endpoint.

### Removal

A check is removed when the layer beneath it starts covering the statement: an assertion, a
`nixosTest`, or the reconciler running it continuously. The checks that predate these rules are
removed when they are touched, not maintained in parallel to a lower layer.

## Verification

1. **Prove the replacement before deleting the original** - measure at the level the consumer sees,
   not "it looks right". Two outages came from skipping this.
2. **A check must be able to fail loudly** - keep `stderr`, derive the exit code from the checks,
   never end a script on a bare `echo`; write the expected value next to the measurement.
3. **Verify per host class before fleet-wide** - one host, then the class, then the fleet.

## Layout

```
flake.nix           inputs, overlays, one mkSystem call per host
hosts/<name>/       entry point: role + hardware + host-specific features
roles/              base → server | pc → desktop | notebook
features/           NixOS modules, discovered by the `nixos.nix` marker, each behind `enable`
  system/  services/  dev/  media/  desktop/
contracts/          domain schemas, projections and owned libraries
inventory/          site facts (subnets, hosts, devices), composed explicitly, never discovered
checks/             evaluation fixtures and generated-artifact assertions
apps/               operational programs: network and exposure audits, package updater
lib/                system composition, module discovery and generic pure helpers
packages/           custom packages and their overlays
user/<name>/        Home Manager: home.nix, packages, shell, editors
media/              wallpapers, avatars and webapp icons
secrets/            SOPS-encrypted, one file
docs/               the specification, see docs/README.md
```

Adding a service: create `features/services/<name>/nixos.nix` with an `enable` option, declare its
contracts, and enable it on the host that runs it.
